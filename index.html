The Work

Three problems, one engine

Verification is the engine of all three: a model can only teach itself, or keep what it learned, if the signal it learns from cannot be fooled.

1. Experience past the frontier Built · first run pending

A small model trains only on its own attempts, each checked exactly, on program-induction tasks whose difficulty has no ceiling. It chooses its own level, and it is compared against the same recipe with coin-flip reward, a fixed curriculum, and a frozen copy. The claim we test is the slope, levels climbed per unit of experience, not a gap to any one model.

2. Continual learning Research

Weights that keep changing with every verified experience, without forgetting what came before. The verifier decides which experiences are safe to keep. Three studies so far, none positive: a forgetting effect we predicted came out in the opposite direction; a per-item learning cap was uninformative under its own pre-set rule; and an agent reflecting on feedback with frozen weights did not clear the bar we set for learning. The next design is registered after the first pillar reads.

3. A verifier beyond human checking Shipped work

Machines that check what humans cannot. We measure how often today's checks are fooled, in benchmarks, RL environments and self-improvement claims, with an independent oracle, and we build the checks that are not.

Evidence So Far

What is measured

Correct signal teaches; random signal does not. In our own reinforcement-learning run on a 1.5B model, reward from an exact checker raised depth-4 composition accuracy by +0.10 (95% interval [+0.04, +0.17]) over a frozen copy, while an otherwise identical run with coin-flip reward did not improve. It did not transfer to an outside math benchmark, and we report that too.

Benchmarks accept broken solutions. Our open tool gameability finds that 17.9% of MBPP problems (169 of 942) and 10.3% of HumanEval problems (16 of 155) accept a deliberately broken solution; 95.2% and 84.6% of those flags are confirmed by EvalPlus's independent tests.

The harness moves the score. The same checkpoint, on the same 250 problems, scored 0.608 under one evaluation scaffold and 0.460 under another, both choices a competent team could defend: a 0.148 gap, against a 0.088 noise floor, with identical weights. A benchmark number reported without its harness cannot be read to better than that.

Vendors' verifiers, audited. We read the public reward and scoring code of the 42 companies that sell RL environments to frontier labs, against a checklist fixed before reading, and confirmed each flag by running the vendor's own code. Results are published here after every affected vendor has been told privately and had the chance to reply.

Tools anyone can run

gameability finds the problems in a code benchmark that accept broken solutions. It breaks each problem's reference solution in one small place, confirms the result is really wrong, then checks whether the problem's own tests notice. Runs on a laptop, no model or API key. Scoreboard & documentation →

$ pip install "gameability[hf]" && gameability check mbpp

rsi-audit checks a self-improvement or agent-leaderboard claim from its public artefacts: whether the ranking survives resampling, whether the agent could see the grader, whether the reported system was picked on the graded tasks, how many record claims could pass by chance, and the 12 requirements a self-improvement number needs.
